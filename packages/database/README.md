# `database`

A Prisma instance to help us talk to a PostgreSQL database. This was generated with `npx prisma init`.

## 🏗️ Modular Schema Structure

The Prisma schema is organized into modular files for better maintainability:

```text
schema.prisma              # Combined schema (generated by scripts/build-schema.js; do not edit)
prisma/schemas/
├── auth.prisma            # User, Session
├── notes.prisma           # Note processing and status tracking
├── images.prisma          # Note and recipe images
├── queue.prisma           # Background job processing
├── parsing.prisma         # Parsed ingredient and instruction lines
├── meta.prisma            # Categories and tags
├── source.prisma          # Sources, URLs, and books
├── ingredients.prisma     # Legacy ingredient identity (replaced by the ontology)
├── recipes.prisma         # Recipes promoted from notes
└── ontology.prisma        # Food ontology, lexicon, mentions, review loop (v2 parser)
migrations/                # One folder per migration
scripts/                   # build-schema, verify-migrations, seeds, exports
```

### Schema Modules

- **`auth.prisma`**: User authentication and session management
  - `User`, `Session`
  - `UserType` enum

- **`notes.prisma`**: Note processing and status tracking
  - `Note`, `EvernoteMetadata`, `NoteStatusEvent`
  - `NoteStatus`, `ErrorCode` enums

- **`queue.prisma`**: Background job processing
  - `QueueJob` model
  - `QueueJobStatus`, `QueueJobType` enums

- **`parsing.prisma`**: Parsed content from recipe notes
  - `ParsedIngredientLine`, `ParsedInstructionLine`, `ParsedSegment`

- **`meta.prisma`**: Categorization and tagging
  - `Category`, `Tag`

- **`source.prisma`**: Source tracking and references
  - `Source`, `URL`, `Book`
  - `SourceType` enum

- **`ingredients.prisma`** (legacy): `Ingredient`, `Alias`, `IngredientReference`, `IngredientCategory`, `IngredientTag`, `Brand`. Retired in Phase 7 of the ingredient rebuild.

- **`recipes.prisma`**: `Recipe`, a curated note that reuses the note's parsed lines.

- **`ontology.prisma`**: the v2 food ontology (Phase 2 of the [ingredient rebuild](../../docs/architecture/ingredient-ontology-rebuild.md#ontology-data-model)).
  - Knowledge: `FoodConcept`, `LexiconEntry`, `AttributeDefinition`, `AttributeValue`, `AttributeApplicability`, `ConceptAttribute`, `PreparationOperation`, `FoodRelationship`, `FoodClassification`, `FoodSubstitution`, `FoodProduct`
  - Corpus: `IngredientMention` with `MentionAttribute`, `MentionPreparation`, `MentionModifier`
  - Review loop: `Discovery`, `DiscoveryEvidence`, `LexiconDecision`, `LexiconRevision`, `ConceptMergeRecord`, `LegacyIngredientMapping`
  - Ids are UUIDv7 stored as native `uuid`. Enum value lists are mirrored in `@peas/parser/v2`, and `src/repository/ontology/__tests__/helpers.test.ts` fails if they drift.

## 🧠 Ontology repositories

`src/repository/ontology/` holds every read and write for the ontology tables; everything is exported from `@peas/database`. Functions return narrow record types, never Prisma models. Write functions take a transaction as their first argument, and read functions take an optional client as their last:

```ts
import { bumpRevision, createConcept, createLexiconEntries, getLexiconSnapshot, prisma } from "@peas/database";
import { buildLexicon, parseLineBest } from "@peas/parser/v2";

await prisma.$transaction(async (tx) => {
  const revision = await bumpRevision(tx, "seed:example");
  const { id } = await createConcept(tx, { canonicalName: "chicken thigh", status: "VERIFIED" });
  await createLexiconEntries(tx, [{ text: "chicken thighs", role: "FOOD", kind: "PLURAL", conceptId: id, status: "ACTIVE" }], revision);
});

const lexicon = buildLexicon(await getLexiconSnapshot());
parseLineBest("1 lb chicken thighs", { lexicon }); // [1 lb] {chicken thighs:FOOD}
```

| Module | Main functions |
| --- | --- |
| `revision.ts` | `getCurrentRevision`, `bumpRevision` |
| `lexicon.ts` | `getLexiconSnapshot`, `createLexiconEntries` (computes `normalized`, `matchKey`, `tokenCount`, `targetKey`; replays are no-ops), `deprecateLexiconEntries` |
| `concepts.ts` | `createConcept` (unique slugs), `getConceptDetail` (with inherited classifications), `searchConcepts`, `setConceptStatus` |
| `relationships.ts` | `addRelationship` (rejects IS_A / PART_OF cycles), `getAncestors`, `getDescendants` |
| `attributes.ts` | `getAttributeVocabulary`, `addAttributeValue`, `setApplicability` |
| `classifications.ts` | `setClassification`, `getEffectiveClassifications` (D15 inheritance) |
| `mentions.ts` | `upsertMentionsForLine` (idempotent; protects verified mentions), `getMentionsForLine`, `getMentionDetail`, `findMentionsByText` (pg_trgm), `markMentionVerified` |
| `discoveries.ts` | `upsertDiscoveries` (counts and priority from evidence), `getDiscoveryQueue` (cursor paging), `getDiscoveryDetail` |
| `decisions.ts` | `recordDecision` (own revision; closes the discovery) |
| `legacy-mapping.ts` | `upsertLegacyMapping`, `getLegacyMapping` |
| `resolver-context.ts` | `loadResolverSnapshot` (everything the resolver needs as one JSON-safe `ResolverSnapshot`: ACTIVE and PROPOSED entries with targets, vocabulary, concepts, relationships, applicability, concept attributes, verified-choice priors, revision) |
| `helpers.ts` | `computeTargetKey`, `slugify`, `uuidv7`, `isUniqueViolation`, `OntologyError` |

The resolver runs on a snapshot, so a new verified entry takes effect on the next load with no grammar change:

```ts
import { loadResolverSnapshot } from "@peas/database";
import { buildResolverContext, processIngredientLine } from "@peas/parser/v2";

const context = buildResolverContext(await loadResolverSnapshot());
processIngredientLine("1 lb boneless chicken thighs", context).mentions[0].status; // "AUTO_RESOLVED" once the entries exist
```

### Seeds

Run in this order; each is idempotent and bumps the lexicon revision only when it writes something.

| Script | What it does |
| --- | --- |
| `db:seed:ontology` | Attribute dimensions, values, and preparation operations from `@peas/parser/v2` |
| `db:seed:modifiers` | The 99 reviewed modifier entries in `packages/parser/fixtures/lexicon/modifiers.seed.json` (ACTIVE), resolved against the vocabulary |
| `db:seed:legacy [--batch 200] [--dry-run]` | Legacy `Ingredient` rows to concepts in three passes, keyed by `LegacyIngredientMapping` so it resumes where it stopped. Pass 1: one- or two-word or reviewed names become concepts with CANONICAL, PLURAL, and ALIAS entries (ACTIVE if reviewed, else PROPOSED). Pass 2: longer names go through the resolver; modifier-composed names ("finely chopped parsley") map to the head concept for review, attribute-composed names ("boneless skinless chicken thigh") become proposed concepts plus an IDENTITY_DECISION discovery, and anything else becomes a proposed concept. Pass 3: parents become RELATIONSHIP_SUGGESTION discoveries (never relationships), properties become LEGACY classifications through `LEGACY_PROPERTY_CLASSIFICATIONS`, categories become CATEGORY classifications, and tags, substitutions, brands (as products), and composed flags carry over onto concepts created from that ingredient. `--dry-run` runs everything in one transaction and rolls it back. |

`db:evaluate:resolution [--limit 5000] [--export-snapshot path]` writes a read-only resolution report over stored lines to `packages/parser/fixtures/reports/resolution.db.md`.

Every JSON column (`syntax`, `quantity`, `resolution`, discovery and decision payloads, decision effects) is validated with its Zod schema from `@peas/parser/v2` on write and on read.

### Constraints outside the Prisma schema

The `add_food_ontology` migration adds what Prisma cannot model: the `pg_trgm` extension, CHECK constraints (a lexicon entry's target must match its role; no self-relationships, self-substitutions, or self-merges), and a partial index for the open review queue. `prisma db push` would silently drop them, so never use it on a database that matters.

## 🚀 Usage

### Development Workflow

1. **Edit modular schema files** in `prisma/schemas/`
2. **Build the combined schema**:

   ```bash
   npm run build:schema
   ```

3. **Generate Prisma client**:

   ```bash
   npm run db:generate
   ```

4. **Create a migration** (see below). Schema changes always go through `yarn db:migrate`; `db:push` is only for throwaway databases, because anything pushed without a migration is missing from every other environment.

### Prisma 7 notes

- Connection settings live in `prisma.config.ts` (not in the schema). The CLI reads `DATABASE_URL` from the environment or the root `.env.local`, and `SHADOW_DATABASE_URL` when set.
- Clients connect through the `pg` driver adapter. Create them with `createPrismaClient()` from `@peas/database` (or `scripts/prisma-client.js` in standalone scripts) rather than `new PrismaClient()`.
- `prisma migrate dev` and `db push` no longer run `prisma generate`; run `yarn build` (or `prisma generate`) after schema changes.

### Available Scripts

- `npm run build:schema` - Combine modular schema files
- `npm run db:generate` - Build schema and generate Prisma client
- `npm run db:migrate` - Build schema, create a migration, and apply it
- `npm run db:verify-migrations` - Replay all migrations on `SCRATCH_DATABASE_URL` and fail if they differ from the schema
- `npm run db:push` - Build schema and push to database (throwaway databases only)
- `yarn db:seed:ontology` - Seed attribute dimensions, values, and preparation operations from `@peas/parser/v2` (idempotent; bumps the lexicon revision only when something was added)
- `yarn db:seed:modifiers` - Seed reviewed modifier lexicon entries (after `db:seed:ontology`)
- `yarn db:seed:legacy` - Seed the ontology from legacy ingredients (`--dry-run`, `--batch <n>`)
- `yarn db:evaluate:resolution` - Resolution report against the live database (read-only)
- `yarn typecheck` - Typecheck sources, tests, and scripts (`tsconfig.test.json`)
- `yarn test:run` - Unit tests (no database needed)
- `yarn test:int` - Unit and integration tests against `TEST_DATABASE_URL` (integration suites skip when unset)
- `yarn test:coverage` - The same run with the coverage floor (see `docs/testing.md`)

## 🧪 Testing

Unit tests need no database. Integration tests run against a throwaway Postgres database; the global setup drops its `public` schema and replays every migration first, and refuses to run unless the database name contains "test" and differs from `DATABASE_URL`.

```bash
createdb peas_test   # once
TEST_DATABASE_URL=postgresql://<you>@localhost:5432/peas_test yarn workspace @peas/database test:int
```

The integration suites cover the vocabulary seed, slug collisions, cycle rejection, classification inheritance, lexicon deduplication and the CHECK constraint, snapshot round-trips into the v2 parser, mention idempotency and verified-mention protection, trigram search, discovery counts and priority, decisions, legacy mappings, and every target interpretation in `packages/parser/fixtures/golden/semantic.json`.

### Adding New Schema Modules

1. Create a new `.prisma` file in `prisma/schemas/`
2. Add the file to the `schemaFiles` array in `scripts/build-schema.js`
3. Run `npm run build:schema` to test

## 📦 Migration & Deployment Workflow

### Creating a Migration

1. **Edit your modular schema files** in `prisma/schemas/` as needed.
2. **Build the combined schema**:

   ```bash
   npm run build:schema
   ```

3. **Create a new migration**:

   ```bash
   yarn db:migrate --name "your_migration_name"
   ```

   This will:
   - Generate a new migration in `migrations/` (next to the combined `schema.prisma`)
   - Apply it to your local/dev database
   - Update the Prisma client

### Applying Migrations to Production

1. **Push your code and migrations to your production environment**.
2. **Build the schema and deploy migrations**:

   ```bash
   npm run build:schema
   npx prisma migrate deploy
   ```

   This will apply all pending migrations to your production database.

### Resetting the Database (Development Only)

If you need to reset your dev database (e.g., after major schema changes):

```bash
npx prisma migrate reset --force
```

This will drop and recreate the database, apply all migrations, and regenerate the Prisma client.

## 📊 Database Schema

The application uses Prisma with PostgreSQL and includes:

- **User Management**: Authentication and user profiles
- **Note Processing**: Recipe content and metadata storage
- **Queue Jobs**: Background job tracking and error handling
- **Parsed Content**: Structured ingredient and instruction data
- **Error Tracking**: Comprehensive error logging and recovery

### Key Models

- `Note`: Recipe content and processing status
- `ParsedIngredientLine`: Extracted ingredient information
- `ParsedInstructionLine`: Processed instruction text
- `QueueJob`: Background job management
- `ParsedSegment`: Structured ingredient data (legacy v1 output)
- `FoodConcept`, `LexiconEntry`, `IngredientMention`: the v2 ontology (see above)
